# Урок 1. Обробка помилок у n8n: Retry, On Error, Error Workflow

## Мета
Після уроку твої workflows не «мовчки падають». Вони повторюють запит при тимчасових збоях, обходять проблемні записи і сповіщають тебе раніше, ніж клієнт помітить проблему.

## Теорія

### 1. Три рівні захисту
| Рівень | Де налаштувати | Коли використовувати |
|---|---|---|
| **Retry On Fail** | Settings ноди | Тимчасові збої: 429, 5xx, таймаути |
| **On Error** | Settings ноди | Що робити, якщо помилка лишилась: зупинитись, продовжити чи піти окремою гілкою |
| **Error Workflow** | Settings workflow | Сповіщення тобі про будь-яке падіння |

### 2. Retry On Fail
У Settings ноди: `Retry On Fail` → `Max Tries` (наприклад, 3) і `Wait Between Tries` (наприклад, 5000 мс). Цього достатньо для більшості збоїв API.

### 3. On Error
- **Stop Workflow**: за замовчуванням. Все зупиняється.
- **Continue**: йти далі, ніби помилки не було. Небезпечно: можна втратити дані непомітно.
- **Continue (using error output)**: у ноди з'являється окремий вихід для помилок. Наприклад, погані записи йдуть у таблицю «на ручну перевірку», а решта обробляється далі. **Найкращий варіант для клієнтських проєктів.**

### 4. Error Workflow
Окремий workflow, який починається з ноди **Error Trigger**. Його вказують у Settings основного workflow (`Error Workflow`). Коли основний падає, n8n запускає цей, передаючи назву workflow, ноду, текст помилки та посилання на виконання.

## Приклади

Error Workflow «Сповіщення про помилки»:
```
[Error Trigger] → [Telegram: Send Message]
```
Текст повідомлення (expression):
```
🔴 Впав workflow: {{ $json.workflow.name }}
Нода: {{ $json.execution.lastNodeExecuted }}
Помилка: {{ $json.execution.error.message }}
Посилання: {{ $json.execution.url }}
```

Важливо: Error Trigger спрацьовує тільки для **автоматичних** запусків (за тригером чи розкладом), а не коли ти натискаєш «Execute» вручну.

## Практика

**Завдання 1.** Створи workflow: Schedule Trigger (кожні 5 хв) → HTTP Request на `https://httpstat.us/503` (завжди повертає помилку 503). Увімкни Retry On Fail: 3 спроби по 3 секунди. Активуй workflow і подивись у Executions, що відбувається.

**Завдання 2.** Створи Error Workflow з Error Trigger і Telegram-сповіщенням (або Email, якщо Telegram ще не налаштований). Підключи його до workflow із завдання 1. Дочекайся сповіщення.

**Завдання 3.** Зроби workflow, що обробляє 5 записів (Code node з масивом). Один запис має неправильний email, через який HTTP Request падає. Налаштуй `Continue (using error output)`, щоб 4 записи пройшли, а поганий потрапив в окрему гілку.

**Завдання 4.** Після перевірки **деактивуй** тестовий workflow із завдання 1, щоб він не спамив.

## Контрольні запитання
1. Яке налаштування допоможе, якщо API іноді повертає 429?
2. Чому On Error = Continue (без error output) небезпечний у клієнтських проєктах?
3. З якої ноди починається Error Workflow і де його підключають?
4. Ти тестуєш workflow кнопкою Execute, він падає, але сповіщення не приходить. Чому?
5. Клієнт надсилає 200 заявок, 3 з них з битими даними. Як зробити, щоб 197 оброблялись, а 3 не загубились?

<details>
<summary>Відповіді</summary>

1. Retry On Fail з паузою між спробами.
2. Помилка ігнорується, і дані непомітно губляться. Ніхто не дізнається про проблему.
3. З Error Trigger. Підключають у Settings основного workflow → Error Workflow.
4. Error Workflow спрацьовує тільки на автоматичні (production) запуски, а не на ручні.
5. On Error → Continue (using error output). Помилкові записи йдуть у гілку, яка зберігає їх для ручної перевірки і сповіщає тебе.
